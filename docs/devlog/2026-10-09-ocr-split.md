# 2026-10-09 Mathpix 연동과 OCR·문제 나누기 검증

- 단계: 로드맵 1단계(OCR·분할 검증)
- 관련 커밋: `Mathpix 연동과 문제 나누기, 1단계 측정 도구`

## 한 일

- Mathpix v3/text 호출(`MathpixOcrEngine`), 재시도(`OcrRetry`), 문제 나누기 추천(`ProblemSplitter`), 정확도 계산(`SplitEvaluation`)을 Java로 만들고, 측정 스크립트가 같은 코드를 CLI(`./gradlew ocrTool`)로 부르게 했다.
- 실제 문제집·시험지 사진 9장으로 측정했다. 호출 9번(1장 연결 확인 + 8장), 비용 약 $0.03.
- 라벨(사진마다 문제 번호)은 내가 초안을 쓰고 기준은 사용자가 정했다(소단원 표시·탐구 단계·예제는 문제 아님, 잘린 문제는 셈).
- OCR 오류 분류는 ocr-evaluator 서브에이전트가 사진과 원문을 대조해 73건을 정리했다.

| 지표 | 결과 |
| --- | --- |
| 분할 재현율 / 정밀도 | 17문제 중 13 찾음(76%) / 추천 16곳 중 13 맞음(81%) |
| 사진 완전 일치 | 9장 중 5장(큰 글씨 6장 중 5장, 작은 글씨 3장 중 0장) |
| 문제당 OCR 오류 | 작은 글씨 6.0건(2문제 통째 누락), 큰 글씨 2.8건 |
| 그림 좌표 | `line_data`의 diagram/chart `cnt`로 옴. 9개 중 8개 정확 |
| 테스트 | 96개(새로 15개). Mathpix는 가짜 서버로만 테스트 |

## 결정과 이유

| 결정 | 이유 | 고려한 대안 |
| --- | --- | --- |
| **응답 본문의 `error` 칸까지 검사** | 공식 문서 확인 결과 Mathpix는 대부분의 오류를 HTTP 200으로 돌려준다. 상태 코드만 보면 "글자 없음" 같은 실패를 성공으로 저장한다 | 상태 코드만 검사 |
| **재시도 여부를 오류 종류로 구분** | 키 오류·사진 오류는 다시 해도 실패하고 요금만 낼 수 있다. 일시 오류(`sys_exception`, 429, 5xx, 연결 실패)만 최대 3회 | 모든 실패 3회 재시도 |
| **요청마다 `improve_mathpix: false`** | 키 설정에서 꺼 두었지만, 키를 새로 만들면 기본값이 켜질 수 있다. 문제집 사진이 외부에 보관되지 않게 코드에서 한 번 더 막는다 | 콘솔 설정만 믿기 |
| **같은 사진은 다시 호출하지 않음**(SHA-256 지문별 캐시) + **호출 장수 제한** | 콘솔에서 한도를 낮출 수 없었다(올리는 신청만 가능). 반복 호출 요금은 프로그램이 막아야 한다. 설계서 5장의 "이미 처리한 사진은 다시 OCR하지 않음"과 같은 원리 | 콘솔 한도에 의존 |
| HTTP 클라이언트는 **JDK `HttpClient` + multipart 직접 작성** | 의존성을 늘리지 않고, 파일 이름(한글)은 헤더를 깨지 않게 확장자만 보낸다 | Spring `RestClient`, OkHttp |
| Mathpix 테스트는 **JDK `HttpServer`로 띄운 가짜 서버** | 테스트가 실제 요금을 쓰거나 키가 필요하면 안 된다. 요청에 보관 끄기·줄 좌표 옵션이 실리는지, 오류별 재시도 여부를 검사한다 | 실제 API로 통합 테스트 |
| 분할 규칙은 **실제 응답을 본 뒤** 정함 | 첫 응답에서 ①이 "(1)"로 오고, 쪽·소단원 번호가 `page_info` 줄로 오는 것을 확인했다. 그래서 `page_info`·표 칸·손글씨 줄을 제외하고, 혼자 있는 숫자는 경계로 보지 않는다 | 설계서 예시 정규식 그대로 |
| 정확도는 **순서까지 맞아야** 맞은 것(최장 공통 부분열) | 번호만 맞고 순서가 뒤바뀌면 검수 화면에서 경계가 틀린다 | 집합 비교 |
| **실패를 규칙으로 덮지 않음** | 실패 6건 중 4건은 OCR이 번호를 잘못 읽은 것이다("운 제 \(4x\)"). 이 한 건에 맞춘 정규식은 과적합이라 후보로만 리포트에 적었다 | 실패마다 패턴 추가 |

## 문제와 해결

- **콘솔에서 사용 한도를 낮출 수 없음**
  - 설계서는 "콘솔에서 한도를 낮게"라고 적었지만, 실제 화면은 올리는 신청만 받았다.
  - Usage Alerts(하루 예상 비용 $1 초과 시 메일)와 프로그램 쪽 장치(장수 제한, 재호출 금지, 재시도 상한)로 바꾸고 설계서 11장을 고쳤다.
- **"Data Retention Opt-Out" 위치를 잘못 안내**
  - 공식 문서만 보고 "콘솔에 스위치가 없다"고 했는데, 실제로는 API 키 설정에 "Improve Mathpix"가 있었다. 문서와 실제 화면이 다를 수 있다는 것을 배웠고, 두 가지(키 설정 + 요청 옵션)를 모두 쓰도록 정리했다.
- **호출했는데 Usage가 0**
  - 응답의 `request_id`로 처리됐음을 확인했고, Usage 집계가 늦게 반영된다고 판단해 사용자 결정으로 진행했다. 콘솔의 Requests 탭은 호출 기록이 아니라 한도 증액 신청 목록이었다(내 안내 오류).
- **서브에이전트가 리포트(.md)를 못 씀**
  - 서브에이전트에서 마크다운 파일 쓰기가 막혀 있어 본문을 메시지로 돌려받아 메인이 저장했다.

## 면접 포인트

- **"외부 유료 API를 붙일 때 무엇을 조심했나요?"** → 비용과 실패 처리. 같은 입력은 해시로 캐시해 두 번 호출하지 않고, 실행당 호출 장수를 제한하고, 재시도는 일시 오류만 3회까지 한다. 공급자 콘솔에서 한도를 못 낮춰서 알림과 코드 쪽 장치로 보완했다.
- **"API가 오류를 200으로 준다면?"** → 문서를 확인해 응답 본문의 `error` 칸을 검사하고, 오류 ID로 재시도 가능 여부를 나눴다. 이를 가짜 서버 테스트로 고정했다.
- **"외부 API를 어떻게 테스트했나요?"** → 테스트 안에서 JDK `HttpServer`로 가짜 서버를 띄워 요청 내용(헤더, multipart, 옵션)과 응답별 동작을 검사했다. 실제 키와 요금이 테스트에 들어가지 않는다.
- **"OCR 정확도를 어떻게 측정했나요?"** → 사람이 정한 라벨과 순서까지 비교(LCS)해 재현율·정밀도를 냈고, 오류는 사진과 대조해 유형별로 셌다. 실패 원인을 OCR 단계와 규칙 단계로 나눠, 규칙을 고칠 문제와 촬영 안내·검수 경고로 풀 문제를 구분했다.
- **"측정 결과로 무엇을 바꾸나요?"** → 글씨 크기가 결정적이어서 촬영 안내(반쪽씩 가까이)를 바꾸고, 신뢰도로 안 잡히는 체계적 오류(자모 분해, 보기 번호 "(1)")는 검수 화면 규칙 경고로 잡는다. 본문은 자동으로 고치지 않는다.
