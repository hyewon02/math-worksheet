# 2026-10-06 데이터 모델과 문제은행·문제지 API

- 단계: 로드맵 4단계 일부를 앞당김(Mathpix 결제 전, 키 없이 가능한 백엔드)
- 관련 커밋: `데이터 모델과 문제은행·문제지 API`

## 한 일

문제은행(DB)의 문제로 문제지를 저장하고, 내려받기 버튼 한 번으로 **원고 조립 → Word 변환 → 빈칸 채우기 → 역변환 비교**까지 끝나는 API를 만들었다. 화면은 아직 없다.

| 구성 | 내용 |
| --- | --- |
| Flyway `V1__init_schema.sql` | 설계서 6장 테이블 전부(13개 + 문제지 번호 시퀀스). FK, CHECK 제약(유형·상태·보기 번호 1~5·그림 소유자 하나·그림 너비), 인덱스. `ddl-auto: validate`로 엔티티와 대조 |
| 엔티티 | Problem(`@Version`), ProblemGroup, Choice, Figure, Tag, Template, Worksheet(`@Version`), WorksheetItem(스냅샷 JSON) |
| 원고 조립 `ManuscriptAssembler` | 스냅샷 → Pandoc 원고. 1번부터 번호, 묶음 `[9~10]`, 풀이 공간 ×0.5/1/2, 수식 밖 `<>`만 이스케이프, `[그림:…]` → cm 크기 그림 |
| 문제은행 API | 검색(교재·학년·유형·태그·정답 미입력·본문), 정답 수정(버전 충돌 409), 그림 |
| 문제지 API | 저장·수정·"최신으로 갱신"·복제, 생성(검사 결과 + 토큰), 내려받기(문제지/정답지/zip) |
| 개발용 데이터 | `dev` 프로필에서 샘플 12문제 자동 입력 |
| 테스트 | 81개(새로 42개). 원고 조립 골든 테스트, MockMvc API 테스트, pandoc을 실제로 돌리는 끝-끝 테스트 |

**결과:** `dev` 프로필로 서버를 띄워 curl로 12문제 문제지를 만들고 생성 → **1.8초, 학생용·정답지 모두 역변환 13/13 일치**, zip 내려받기, Word에서 머리말(학원명·제목·날짜·WS-0001) 확인.

## 결정과 이유

| 결정 | 이유 | 고려한 대안 |
| --- | --- | --- |
| 문제지 문항에 **문제 내용 스냅샷(JSON)** 저장 + 스냅샷 당시 version | 저장된 문제지를 다시 내려받으면 만들 당시 그대로 나와야 한다(재출제). 문제가 고쳐지면 version 비교로 "수정됨"을 알리고, 갱신은 선생님이 고른다. 원본이 지워져도 문제지는 재현된다(`ON DELETE SET NULL`) | 문제 id만 참조: 문제를 고치면 예전 시험지가 바뀜 / 문제 버전 테이블: 3만 문제 규모에 과함 |
| 스냅샷은 정규화하지 않은 **JSON 한 칸** | 스냅샷은 통째로 읽고 쓰는 값이고 조회 조건으로 쓰지 않는다. 모르는 칸은 무시하게 해 나중에 칸이 늘어도 예전 스냅샷을 읽는다 | 스냅샷 전용 테이블 여러 개: 조인만 늘어남 |
| **낙관적 잠금**(`@Version`) + 요청에 version을 받아 직접 비교 | 로그인 없이 여러 선생님이 동시에 쓴다. 충돌은 드물고, 생기면 "다른 분이 먼저 수정했습니다"로 다시 불러오면 된다. JPA `@Version`만으로는 "화면이 불러온 시점"의 version을 모르므로 요청 값과 비교한다 | 비관적 잠금: 검수 화면을 열어 둔 채 자리를 비우면 잠김 |
| 문항만 바뀌어도 **문제지 version을 올림**(`touch()`) | 순서·풀이 공간은 자식 엔티티(WorksheetItem)라 바뀌어도 부모 `@Version`이 오르지 않는다. 두 선생님이 같은 문제지 순서를 동시에 바꾸면 충돌을 못 잡는다 | `OPTIMISTIC_FORCE_INCREMENT` 잠금: 같은 효과지만 수정 시각도 함께 바뀌는 쪽이 목록 정렬에도 맞음 |
| **DB 읽기는 짧은 트랜잭션, Pandoc 실행은 트랜잭션 밖** | Pandoc 변환은 1~2초 걸린다. 그동안 DB 커넥션을 잡고 있으면 동시 요청에서 커넥션 풀이 마른다. `TransactionTemplate`으로 필요한 값만 꺼내 두고 변환한다 | 메서드 전체 `@Transactional`: 간단하지만 커넥션 점유 |
| 내려받기를 **두 단계**(만들기 → 토큰으로 받기, 1시간 보관) | 역변환 불일치·그림 누락이면 차이를 보여주고 "확인했음, 내려받기"를 받아야 한다(설계서). 한 요청으로는 검사 결과를 보여줄 틈이 없다 | 응답 헤더에 검사 결과: 화면이 다운로드 전에 볼 수 없음 |
| 원고 조립은 **상태 없는 순수 함수** | DB 없이 단위 테스트하고, 같은 입력이면 같은 원고가 나온다 | 서비스 안에서 바로 문자열 조립 |
| **골든 테스트**: DB에 넣은 샘플 → 조립 결과 = 손으로 쓴 `sample-01.md` | `sample-01.md`는 Word 역변환 13/13을 통과한 원고다. 조립 결과가 글자 단위로 같으면 "DB → 원고" 구간도 본문을 바꾸지 않았다는 증명이 된다 | 조립 결과 일부만 `contains`로 검사: 공백 하나 차이도 못 잡음 |
| 본문 검색은 **LIKE + 검색 전용 칸** | LaTeX 명령어·공백을 걷어 낸 칸을 따로 둬서 "등비 수열", "등비수열" 모두 찾는다. 3만 건 LIKE는 수십 ms(설계서) | 전문 검색 엔진: 한국어 형태소 분석이 필요하고 설치형 앱에 과함 |
| 검색 조건은 **Specification**으로 조합 | 6개 조건이 모두 선택이라 경우의 수만큼 쿼리 메서드를 만들 수 없다. 태그 조건만 join + distinct | QueryDSL: 의존성·코드 생성 추가 |
| 스키마는 설계서 6장 **전부를 V1에** | 나중 단계 테이블(OCR 작업 등)도 관계가 정해져 있다. 엔티티는 지금 쓰는 것만 만들었다(`validate`는 매핑된 엔티티만 검사) | 단계마다 마이그레이션: 초기 설계를 한눈에 보기 어려움 |
| 설계서에 없던 칸 3개 추가 | 묶음 안 순서(`group_order`), 그림 표시 이름(`figure.marker`, 본문 `[그림:…]`과 파일을 잇는 키), 형식의 단 너비·보기 기준 칸 수. 모두 원고 조립에 필요 | — |

## 문제와 해결

- **`DownloadStore` 빈 생성 실패("No default constructor found")**
  - 원인: 테스트용으로 시계(`Clock`)를 주입받는 생성자를 하나 더 만들었더니 Spring이 어느 생성자를 쓸지 정하지 못했다.
  - 해결: 운영용 생성자에 `@Autowired`. 테스트는 패키지 전용 생성자로 시간을 앞당겨 만료를 검사한다.
- **zip 내려받기가 MockMvc에서 500**
  - 원인: `StreamingResponseBody`는 비동기로 처리되어 MockMvc에서 `asyncDispatch`가 필요하다.
  - 해결: 두 파일 합쳐 수십 KB라 스트리밍이 필요 없다. 메모리에서 zip을 만들어 `byte[]`로 보냈다(단순한 쪽을 택함).
- **dev 서버를 띄우자마자 요청하면 문제은행이 비어 있음**
  - 원인: `ApplicationRunner`(샘플 입력)는 서버가 요청을 받기 시작한 뒤에 돈다. 헬스체크가 먼저 응답한다.
  - 영향: 개발용 데이터라 문제없음. 단, 내장 형식 등록도 Runner라 배포본에서 켜자마자 문제지를 만들면 형식이 없을 수 있다 → 6단계(배포)에서 기동 순서를 다시 본다.
- **Git Bash에서 curl 인자로 넘긴 한글이 UTF-8로 안 감**
  - 서버는 "요청 내용을 읽을 수 없습니다"(JSON 파싱 실패)로 정상 응답했다. 요청 본문을 UTF-8 파일로 써서 `--data-binary @file`로 보냈다. 화면(브라우저)은 항상 UTF-8이라 앱 문제는 아니다.
- **zip 안 한글 파일 이름이 `unzip -l`에서 깨져 보임**
  - zip의 UTF-8 플래그(0x800)와 실제 바이트(`율현` = `ec9ca8 ed9884`)를 확인해 표시 도구 문제임을 확인했다. Windows 탐색기는 이 플래그를 읽는다.

## 면접 포인트

- **"저장된 문제지는 문제가 바뀌면 어떻게 되나요?"** → 담을 때 문제 내용을 스냅샷으로 복사하고 당시 version을 같이 저장한다. 다시 열면 현재 version과 비교해 "수정됨"을 표시하고, 갱신은 선생님이 고른다. 시험지 재현성과 최신 반영을 사용자가 선택하게 한 것.
- **"동시 수정은 어떻게 막았나요?"** → 로그인이 없는 다중 사용자 환경이라 낙관적 잠금. 화면이 불러온 version을 요청에 실어 보내 비교하고, 다르면 409. 자식 엔티티만 바뀌면 부모 version이 안 오르는 JPA 동작을 알고 `touch()`로 보완했다.
- **"외부 프로세스 호출과 트랜잭션을 어떻게 나눴나요?"** → 몇 초 걸리는 Pandoc을 트랜잭션 안에서 돌리면 커넥션을 점유한다. 읽기 전용 `TransactionTemplate`으로 필요한 값만 꺼낸 뒤 변환했다. 지연 로딩 프록시는 트랜잭션 안에서 초기화해 둔다.
- **"생성 결과가 맞는지 어떻게 보장하나요?"** → 세 겹. ① 원고 조립 골든 테스트(DB → 원고가 기준 원고와 글자 단위로 같음) ② 생성할 때마다 역변환 비교(원고 ↔ Word) ③ 그림 누락·빈칸 잔존 검사. 불일치여도 막지 않고 보여준 뒤 사람이 결정한다.
- **"테스트는 어떻게 구성했나요?"** → 순수 로직(조립·이스케이프·검색 텍스트)은 단위 테스트, API는 `@SpringBootTest` + MockMvc + `@Transactional` 롤백, Word 생성은 pandoc을 실제로 돌리는 끝-끝 테스트. 테스트 데이터는 개발용 샘플과 같은 JSON을 써서 한 벌로 관리한다.
