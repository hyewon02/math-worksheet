## 결정과 이유

| 결정 | 이유 | 고려한 대안 |
| --- | --- | --- |
| **Word 생성 로직을 2단계부터 Java로 구현**하고 개발용 스크립트는 Java CLI(`./gradlew docxTool`)를 부른다 | 설계서는 "2단계 스크립트 검증 → 4단계 Java 이식"이었다. 그러면 같은 로직이 Python·Java 두 벌이 되고, 검증한 것과 실제 앱이 다를 수 있다. 처음부터 한 벌로 만들었다 | Python으로 먼저 검증: 빠르지만 이식 때 다시 검증해야 함 |
| 핵심 부품은 **Spring에 의존하지 않는 일반 클래스**, `@Configuration`에서 빈으로 묶음 | 같은 코드를 앱·CLI·단위 테스트에서 그대로 쓴다. CLI는 Spring 컨텍스트를 띄우지 않아 빠르다 | `@Service`로 바로 작성: CLI에서 쓰려면 컨텍스트를 띄워야 함 |
| 역변환 결과를 **마크다운 텍스트가 아닌 Pandoc JSON AST**로 읽어 비교 | 마크다운 출력은 이스케이프(`\<`)·줄바꿈 위치가 바뀌어 정규식 파싱이 깨지기 쉽다. AST는 `custom-style` 속성으로 문제 경계를 정확히 자를 수 있다 | `-t markdown` 출력을 정규식으로 파싱 |
| 정규화는 **비교용으로만**, 규칙은 설계서 목록에 있는 것만 | 본문 불변 원칙. 비교가 실패할 때 규칙을 넓히면 진짜 변환 오류도 같이 덮인다. 새 규칙은 사용자 승인 + 설계서 기록 + 테스트 | 실패할 때마다 정규화 추가 |
| `PandocRunner`는 stdout·stderr를 **파일로 리다이렉트** | 파이프로 받으면 출력이 큰 경우 OS 파이프 버퍼가 차서 자식 프로세스가 멈출 수 있다(교착). 시간 제한·강제 종료도 넣었다 | `getInputStream()` 읽기: 별도 스레드 두 개가 필요 |
| 빈칸 채우기는 **단락 단위로 run을 이어 붙여** 찾는다 | Word는 `{{시험제목}}`을 `{{시험` + `제목}}`처럼 쪼개 저장하기도 한다. run 하나씩 찾으면 놓친다. 입력값에 `{{…}}`가 있어도 무한 반복하지 않게 바꾼 위치 뒤에서 다시 찾는다 | run 단위 문자열 치환 |
| 보기 배치 기준을 **형식별 설정**(`naesin-2col.json`)으로 | 설계서의 9/15칸은 2단 10pt에서 넘쳤다(미리보기로 확인). 단 너비·글자 크기는 형식마다 달라 고정값이 맞을 수 없다 | 수식 기호를 넓게 세기: 형식이 바뀌면 또 틀림 |
| 테스트용 docx는 **POI로 코드에서 생성** | 바이너리 픽스처를 저장소에 두면 무엇을 검사하는지 안 보이고 갱신도 어렵다 | `src/test/resources`에 docx 파일 |
| 서브에이전트(docx-builder)에 형식 파일·필터·미리보기를 맡기고 메인은 Java를 동시에 작성 | OOXML·Lua 지식과 미리보기 이미지가 컨텍스트를 많이 차지한다. 원고 규격을 먼저 확정해 둘이 같은 계약으로 따로 일했다 | 한 에이전트가 순서대로 |

## 문제와 해결

- **pandoc 실패 시 "실행할 수 없습니다"라는 엉뚱한 오류**
  - 증상: 없는 파일을 넘긴 테스트에서 종료 코드·오류 내용 대신 "pandoc을 실행할 수 없습니다"가 나왔다.
  - 원인: Windows에서 pandoc 오류 메시지 속 파일 이름이 **CP949**로 나온다(`bef8 b4c2` = "없는"). UTF-8로 엄격하게 읽다 `MalformedInputException`(IOException의 하위 클래스)이 났고, 실행 실패용 catch로 잘못 흘러갔다.
  - 해결: stderr는 UTF-8로 읽다 깨지면 시스템 기본 인코딩으로 다시 읽는다. stdout은 pandoc이 항상 UTF-8이라 엄격하게 둔다.
  - 배운 점: 외부 프로세스의 출력 인코딩은 stdout·stderr가 다를 수 있다. 예외 계층(IOException)을 넓게 잡으면 원인이 다른 오류가 같은 메시지로 뭉개진다.
- **Gradle을 거친 CLI 출력의 한글 깨짐**
  - 원인: 자식 JVM → Gradle 데몬 → Gradle 클라이언트로 출력이 전달되며 각 단계가 자기 기본 인코딩(CP949)으로 다시 인코딩했다.
  - 해결: CLI JVM에 `stdout.encoding=UTF-8`, 데몬에 `file.encoding=UTF-8`(gradle.properties), 스크립트가 클라이언트를 부를 때 `JAVA_OPTS`로 UTF-8을 지정.
- **Gradle `JavaExec`가 CLI 종료 코드를 전달하지 않음**
  - 불일치(종료 코드 1)가 Gradle 빌드 실패로 길게 찍혔다. `ignoreExitValue`로 두고 CLI가 마지막 줄에 `exit=N`을 찍어 스크립트가 읽는다.
- **역변환 불일치 2건 → 정규화 규칙 추가(사용자 승인)**
  - 표: Pandoc이 수식으로 끝나는 표 칸에 폭 없는 공백(U+200B)을 붙인다. 화면에 안 보이는 글자라 CLI가 `<U+200B>`로 드러내게 했다.
  - cases: Word 수식에는 cases가 없어 `\left\{\begin{matrix}…\right.`로 돌아온다. Word에는 올바르게 보이는 것을 미리보기로 확인한 뒤, cases 전용 규칙만 추가했다(다른 matrix는 그대로).
  - 두 경우 모두 "규칙을 넓히면 진짜 오류도 덮일 수 있다"는 이유로 스스로 정하지 않고 사용자에게 물었다.
- **묶음 번호를 문제 번호로 오인**
  - 필터가 묶음 지문 앞에 `[9~10]`을 ProblemNumber 스타일로 붙여서, 추출기가 "910번 문제"로 읽을 뻔했다. 서브에이전트 보고서를 보고 실행 전에 고쳤고, 테스트 픽스처에도 `[2~3]`을 넣었다.
- **Word의 표 너비 비율은 단 너비 기준**
  - Pandoc이 쓴 44%를 Word가 본문이 아니라 단 너비에 곱해 표가 3.6cm로 좁아졌다. 필터가 단 기준 비율(0.934)로 환산한다(서브에이전트가 미리보기로 발견).

## 면접 포인트

- **"외부 프로그램(Pandoc)을 Java에서 어떻게 안전하게 실행했나요?"** → `ProcessBuilder`로 실행하고 stdout·stderr를 파일로 리다이렉트해 파이프 버퍼 교착을 피했다. `waitFor(timeout)` 후 `destroyForcibly`, 종료 코드·stderr를 담은 예외, 작업 폴더 임시 파일 정리. Windows 인코딩 문제를 테스트로 발견해 고쳤다.
- **"생성한 문서가 맞는지 어떻게 검증하나요?"** → 만든 docx를 다시 Pandoc으로 읽어(역변환) 원고와 문제별로 비교한다. LaTeX와 Word 수식은 직접 비교가 안 되니 Pandoc이 되돌려준 LaTeX를 최소한의 규칙으로 정규화한다. 규칙은 명시적 목록이고, 늘릴 때는 근거를 설계서에 남긴다. "검증 로직이 실패를 덮지 않게" 하는 것이 핵심.
- **"왜 JSON AST로 비교했나요?"** → 텍스트 파싱은 포맷 세부사항에 묶인다. AST는 구조(스타일 이름, 수식 노드)가 그대로 있어 문제 경계와 수식 개수를 정확히 셀 수 있다.
- **"Spring 없이 동작하는 클래스로 만든 이유는?"** → 같은 로직을 웹 앱, 개발용 CLI, 단위 테스트에서 재사용하려고. 프레임워크는 조립(@Configuration)만 맡는다.
- **"테스트에서 외부 프로그램 의존은 어떻게?"** → pandoc이 필요한 테스트는 `assumeTrue`로 없으면 건너뛰고, CI에는 pandoc을 설치하고 `pandoc --version` 단계로 설치를 강제 확인해 CI에서 조용히 건너뛰는 일이 없게 했다.
