## 결정과 이유

| 결정 | 이유 | 고려한 대안 |
| --- | --- | --- |
| 프론트 빌드 결과를 Spring Boot static 폴더에 넣어 **한 프로그램으로 배포** | 학원 PC 한 대에 설치 파일 하나로 깔아야 한다. 포트·프로세스가 하나면 선생님이 관리할 것이 없다 | 프론트 별도 서버(Nginx): 학원 PC에 설치·운영 부담 |
| `SpaForwardController`가 `/api`와 점(.)이 있는 경로를 뺀 모든 경로를 `index.html`로 forward | React Router 경로(`/bank`)를 새로고침해도 404가 나지 않게. `/api` 오타는 HTML이 아닌 404로 받아야 프론트에서 오류를 구분할 수 있다 | 해시 라우터(`/#/bank`): 주소가 지저분하고 북마크 공유에 불리 |
| H2 파일 모드 + JPA + Flyway, `ddl-auto: validate` | 별도 DB 설치 없이 JPA 기본 지원. 3만 문제 규모 충분. 실행 중 `BACKUP TO`로 백업 가능. 스키마는 Flyway로만 바꿔 설치된 학원 PC의 DB도 업데이트 때 안전하게 올라간다 | SQLite: JPA 방언 추가 필요 / `ddl-auto: update`: 운영 DB에서 예측 불가한 변경 |
| 런타임 데이터를 `%APPDATA%\MathWorksheet`에, 경로는 `AppPaths`로만 | 재설치·업데이트에도 문제은행이 남는다. 경로 계산을 한 곳에 모아 테스트에서 임시 폴더로 바꾸기 쉽다 | 설치 폴더 아래: 업데이트 때 지워지거나 권한 문제 |
| `OcrEngine`, `ImageStorage`를 인터페이스로 분리 | Mathpix 가격·정책 변경이나 클라우드 이전 때 구현체만 바꾼다 | 처음부터 구현체 직접 사용: 지금은 단순하지만 테스트에서 가짜 OCR로 바꾸기 어렵다 |
| API 키는 `MathpixCredentialsProvider` 하나로만 읽고, 우선순위는 설정 화면 > `application-local.yml` > 환경 변수 | 키 접근 지점이 하나라 노출 경로를 통제하기 쉽다. 배포 후에는 선생님이 설정 화면에서 넣은 학원 키가 개발 키를 이긴다 | `@Value`로 곳곳에서 주입: 키 출처가 흩어진다 |
| `MathpixCredentials.toString()`과 화면 표시는 `••••1234` | 로그에 객체를 그대로 찍어도 키가 새지 않게 기본값을 안전하게 | 로그 찍을 때마다 주의: 실수 한 번이면 유출 |
| Provider에 패키지 전용 생성자(설정 파일 경로, 로컬 설정, 환경 변수 함수) | `System.getenv`를 `Function<String,String>`으로 받아 단위 테스트에서 환경 변수를 흉내 낸다. Spring 없이 빠르게 우선순위를 검증 | `@SpringBootTest`로 검증: 느리고 실제 환경 변수에 영향받음 |
| CI를 `windows-latest`에서 실행 | 배포 대상이 Windows이고, 이후 jpackage+WiX 설치 파일도 Windows에서만 만들 수 있다 | ubuntu: 빠르지만 경로·인코딩 문제를 놓칠 수 있음 |

## 문제와 해결

- **로컬 JDK 17, 프로젝트는 Java 21**
  - Gradle 툴체인 + `foojay-resolver-convention` 플러그인으로 빌드 때 JDK 21을 자동으로 내려받게 했다. 개발 PC에 JDK를 맞춰 설치하지 않아도 같은 버전으로 빌드된다.
- **로컬 Node 22.13.1 (프로젝트 요구: 22.14 이상)**
  - 22.13 이하는 한글이 들어간 경로에서 크래시하기 때문에 22.14 이상으로 정했다. 지금 경로(`D:\mathsheet`)는 영문이라 빌드는 통과했지만, `engines`에 명시하고 Node를 올리기로 했다.
- **첫 푸시 거부: `refusing to allow an OAuth App to create or update workflow`**
  - 원인: gh CLI 토큰에 `workflow` 권한이 없으면 `.github/workflows/` 파일을 푸시할 수 없다. 보안상 CI 정의 변경은 별도 권한으로 분리돼 있다.
  - 해결: `gh auth refresh -h github.com -s workflow`로 권한을 추가한 뒤 푸시했다.
- **첫 CI 실행 경고: Node 20 기반 액션 지원 종료, `setup-java@v4` 업데이트 중단**
  - 빌드는 통과했지만 `actions/checkout`·`setup-java`·`setup-node`를 v5로 올렸다. 경고를 쌓아 두면 나중에 갑자기 CI가 깨진다.
- **Pandoc 미설치**
  - 2단계(Word 생성)부터 필요하다. 개발 PC의 PATH에 설치해야 한다.

## 면접 포인트

- **"왜 프론트와 백엔드를 한 JAR로 묶었나요?"** → 사용자가 비개발자이고 서버가 학원 PC 한 대다. 운영 대상(프로세스, 포트, 설치 파일)을 하나로 줄이는 것이 이 서비스의 핵심 요구였다. 대신 SPA 새로고침 문제를 forward 컨트롤러로 해결했고, `/api`는 forward 대상에서 빼서 API 404를 HTML로 감추지 않게 했다.
- **"API 키 관리는 어떻게 했나요?"** → 키를 읽는 경로를 Provider 하나로 모으고, 출처별 우선순위를 정하고, `toString`을 마스킹해 로그 유출을 기본적으로 막았다. `.gitignore`로 `application-local.yml`을 제외하고 예시 파일만 커밋했다.
- **"H2를 운영에 써도 되나요?"** → 동시 접속 몇 명, 3만 건 규모의 단일 PC 앱이라 충분하다. 설치형이라 외부 DB를 둘 수 없다는 제약이 더 크다. 스키마 이력은 Flyway로 관리해 업데이트 때도 데이터가 안전하다.
- **"테스트 전략은?"** → 기능 코드와 테스트를 같이 커밋하고, 테스트 이름은 한국어로 동작을 설명한다(예: `설정_파일이_가장_우선한다`). 외부 의존(환경 변수, 파일)은 생성자 주입으로 바꿔 끼워 단위 테스트한다.
